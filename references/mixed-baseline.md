# 固定多 skill 协作基线

## 参与范围

每轮完整新任务对比，以及调整候选后的完整重跑，固定加入 `id: mixed-baseline, kind: mixed-baseline, display_name: 多 skill 协作基线`；保留 `kind: baseline` 的普通提示词基线。普通候选仍各自独立使用自己的 skill/toolkit，不互看产物。

用户仅选择优化、重做或接续指定方案时，不擅自扩大范围追加基线；选中多 skill 协作基线则继续使用其组合和自己的成果。完整对比时无法运行组合基线应保留 blocked 状态和原因，不能悄悄省略或假装已组合。

## 优先按子任务组合

1. 看到任何结果前分解任务，优先寻找至少两个适配 skill 的互补优势，例如文献检索、研究假设、实验设计、审查与表达。不是为了数量拼凑，无实质子任务可分或不足两个可用 skill 时报告限制。
2. 优先使用本轮已审查并固定快照的候选；需要额外专长时先补充调查、核验和快照，不偷换模型或权限。所有组成 skill 仍遵守 stars ≥500 的规则，除非用户明确指定该 skill；指定“混合基线”本身不豁免所有成员的星数。
3. 冻结成员清单 `members`（每项记录 id、来源、版本、stars/核验日期、用户指定例外依据）、子任务分工与汇合方式。单一工具包的多个模块仍属于一个候选单位，不能冒称多个独立 skill；必要时说明比较边界。
4. 创建独立协作代理，可按任务需要顺序调用或通过自己的子代理并行调用不同成员，最后由该分支内部整合成完整结果。各成员只接收该分支允许的输入，内部可以交接产物；禁止读取任何独立候选/普通基线的答案、评估分数或协调者排名偏好。这不是事后把优胜答案拼起来。
5. 使用相同任务材料、输出要求、评分标准和 Codex 模型，内部代理也遵守模型一致；预算不要求相同，但实际调用次数、时间、可得 token/费用单独记录，不能将更多资源造成的收益归因于组合方法本身。
6. execution.json 中记录 `members_used`、`subtask_assignments`、每项对应产物与实际贡献、内部整合/冲突处理及失败降级。没有实际使用的成员不得列为已调用。成员只有一个成功时标记组合执行不完整，不能包装成多 skill 协作成功。

## 评估与展示

同其他方案一起匿名评估，评分规则不因“组合”身份加分或改权重；不得提前把身份、成员或自评分给裁判。方案正文不可避免暴露方法时说明盲评局限。解盲后显示“多 skill 协作基线”，成员与分工放在末尾折叠运行记录中；正文依旧完整显示，评估在最后。

基线的 stars 不相加、不显示虚构的组合仓库热度。优缺点说明相对独立方案是否有新增收益、内部不一致或成本增加。组合胜出不证明每个成员都优于独立候选。两条基线都不参与“自动移除评分最低的两个 skill”；用户可以明确选择某条基线优化或接续。

`discovery.json` 中协作项使用 `kind: mixed-baseline` 和完整 `members` 数组；运行 `check-selection` 会逐成员检查星数资格。manifest/mapping 复制成员元数据，但 judge-packet 仅包含交付物，execution.json 和成员身份保留在包外。组合后续的 handoff 包含所有成员快照与分工，仅继承该组合分支的原稿。
