# 优化、重做与接着做

## 会话内点选与输入

先交付结果和推荐依据，再使用原生提问控件；不能以代码块或 Markdown 列表冒充真实按钮。`report` 生成 interaction.json，包含 action、selection、adjustment 三组问题参数和 label→variant_id 映射。协调者读取后按实际阶段调用可用工具，例如 `functions.request_user_input_async(payload.action)`；JSON 文件本身不会弹出控件，也不直接运行模型。

1. **选择动作**：展示“优化已有方案、重做已有方案、满意，接着做下一项任务、都不满意，调整候选 skill、先保留，暂不继续”。用户可点选，也可直接写完整要求。已经说清楚操作时跳过此步。
2. **选择结果与补充要求**：用 `selection` 的本轮真实名称和简短特点作为选项，如“marketing-design — 四阶段清楚、排名附理由”。可点一个；若工具只支持单选，不声称支持复选框，而在题目明确提示“多项请在输入框写名称”。优化/继续的要求可在同一自由回复中给出；只有缺少必要信息才追问。重做时按需增加“全部方案”选项。
3. **都不满意**：调用 `adjustment`，同时提供“增加 2 款新 skill / 不增加”和“保留现有候选 / 指定移除 / 移除评分最低的两款（列出真实名称）”。两个选择可组合，也接受“只增加”“只移除”“还是优化某方案”等自由输入。选择“指定移除”但没给名字时，再用真实候选名称询问移除哪些。下一轮要求如已给出，直接沿用。
4. **等待真实回复**：默认预选不是用户同意；不设倒计时自动执行。收到具体操作后简短告知将保留、增加和移除什么，然后执行，无需再加一道确认。每次只执行一个明确的新轮次。

有异步提问工具时发送问题后结束本轮等待回复，不进行依赖该回复的生成；可以先整理现有结果。只有计划模式提问工具时必须遵守其模式限制。没有可用原生控件时明确当前只能文字回复，提供相同的简短选项，不声称 skill 能自行改造客户端界面。不为功能演示而触发真实用户任务或更换候选。

方案名称与特点来自实际结果；不要把示例 marketing-design 固定成所有任务的候选。manifest 可附 display_name、skill_id、kind（skill/baseline）；同名 skill 加结果短标题区分。字母只用于内部盲评，展示时附真实名称。用户说“第一名”且并列时澄清；跨轮指代不明时先定位轮次。人工认可不修改评分，也不自动授权后续执行。

## 增加与移除候选

- `adjust` 表示调整下一轮名单。默认增加 2 款不同于已试过候选的新 skill，也可明确不增加、只移除。先读本任务链 discovery、快照和版本，按新反馈调查、核验、注册及快照。不能把同一 skill 的改名或升级伪装为新候选。找不到两款时说明实际数量与原因，不拿不适配的凑数。
- 指定移除按真实 variant ID 记录。自动低分移除只考虑父轮已完成且 eligible、有有效评分的 skill，不把普通提示词基线当 skill，也不把失败或待核验项当零分。按本轮质量总分选最低两款；若与第三低在预设并列区间内，或不足两款有效评分，先展示具体情况让用户按名称选择。只使用同轮同标准分数。
- `remove=lowest-two` 的脚本检查与界面所列名称必须一致；用户看到后若结果发生变化，重新展示变化，不悄悄换删项。“保留现有候选＋不增加”不启动空操作，提示可优化、重做或暂时结束。
- 保留候选和新增候选使用原任务、共同输入及已给反馈，各自重新完成一次，再用本轮冻结标准匿名评估。默认不带入被否定的答案，不复用旧分数，也不强制补足最初 3–5 款。基线若保留则重新运行，不因增删另外追加基线。
- lineage 保存移除 ID、计划新增数量、保留 ID；调查完成后补充真实新增 ID/来源/版本和最终名单。未完成调查时保持 discovery-required，不启动生成。所有文件保留；后续从祖先查找满意方案时排除已退出当前分支的候选，除非用户明确重新选回。

## 操作语义

| 动作 | 本轮输入 | 候选范围 |
| --- | --- | --- |
| select：满意/先保留 | 只记录选择，不生成 | 一个或多个明确方案 |
| refine：优化 | 原任务、共同材料、自己的原稿、用户修改要求 | 所选方案对应 skill |
| redo：重做 | 原任务与共同材料、用户新要求；不加载旧答案 | 指定方案，或明确的全部参赛项 |
| adjust：调整候选 | 原任务、共同材料及新要求，不带旧答案 | 保留候选＋新调查候选 |
| continue：接着做 | 新任务、已确认事实与约束、各自已选成果及来源 | 明确指定或本任务链已保留的方案 |

refine 必须有可执行的改进要求；用户仅说“优化一下”但当前对话已有具体不满时直接使用该反馈。continue 需要下一项任务，只有“满意某方案”时记录选择并提示“下一步想做什么？”，不自动编造写作或实验任务。已有选择后用户说“接着设计实验”，直接沿用该任务链的选择，不再问一次选谁。与当前链无关的新任务走首次调查。

“全部”指明确父轮全部实际参赛项；若包含普通提示词基线，应直说它也会重做，不能把它伪称为 skill。指定“全部 skill”则不含基线。用户可以改选、同时保留多个，或明确从较早轮次继续。

## 上下文、版本与新一轮

1. 协调者解析用户自然语言，核对父轮编号→variant→实际 skill、版本和来源。优先使用原快照，检查可用性及新任务适配度；原 skill 无法完成新任务时说明缺口并让用户决定换用候选，不静默换 skill。旧版不可用或需要升级时说明版本差异。
2. 用 feedback 记录选择；用 followup 新建子运行及 lineage.json。这是文件辅助工具，不会启动代理。必须传入真实 variant ID，不能把匿名字母直接当作 ID。运行编号由协调者生成，用户无需提供。
3. 将每条分支的 skill 来源、快照哈希、原始材料和需继承的成果整理成 `handoffs/VARIANT_ID/`。共同事实和用户更正放共同输入；分支原稿与来源只给该分支。多项默认分别接续各自原稿，不互看、不融合。只有用户明确要求同一底稿时才把指定底稿作为共同输入，记录这项区别。
4. 新建独立生成代理，只传任务、该分支 handoff、对应 skill 和新输出目录。接续靠文件，不依赖旧代理仍然存活。提示词见 prompts.md。同一轮模型一致；若跨轮当前模型变化，记录变化，不声称与旧轮可直接比较。仍不要求相同预算。
5. refine/redo 默认继承原评分标准，结合新要求在生成前检查是否需更新；continue 为新任务重定标准。修改要求不是来自裁判的秘密排名提示。新评估代理可见完成本轮核验所需的匿名分支输入与要求，不能看到旧分数、用户选中原因或 skill 身份。必须披露不同分支继承材料不同，因此比较的是接续后的完整成果，而非纯 skill 因果效果。
6. 多方案做本轮匿名比较；单方案仍用独立评估者检查要求满足度并反馈缺口，报告只称“质量检查”，不把唯一方案包装成胜出。不把不同任务或评分标准下的分数串成升降榜。
7. 每项只执行一次约定迭代，基础设施重试遵循原协议；结束后交付新结果与父轮链接，再提供反馈入口。绝不无限自动优化。用户沉默时保持等待，不启动下一阶段。

原结果、旧评估和已确认成果不覆盖。feedback 事件保留实际用户措辞；state.json 只是方便恢复选择的索引，不代替原始事件。新任务生成完成前不把未完成的新结果设为已认可；选择仍可指向父轮。详细字段与命令见 storage.md。

多 skill 协作基线作为独立可选分支：沿用其成员快照、分工与自身成果，不能只按单一 skill_id 准备 handoff。用户仅选部分方案时不自动补基线；完整调整重跑则重新执行普通提示词和多 skill 协作两条基线。
